# Build and release automation

`.github/workflows/build-release.yml` adapts [qsh's workflow](https://github.com/abdulrahman1s/qsh/blob/master/.github/workflows/build-release.yml) and keeps its manual inputs, conventional-commit conventions, skip markers, cached Rust builds, named archives, checksums and generated notes. This project supports only `x86_64-unknown-linux-gnu`.

Every push and pull request runs formatting, locked Clippy/tests, strict TypeScript checks, Prettier formatting, compiled extension version/assets validation, Bun TypeScript timing/session/policy tests, Bun release/installer tests, a CPU-only isolated Chromium recovery test, release compilation, an archive install/native-host smoke test, Nix formatting, and `nix flake check`/`nix build`. GPU checks are explicitly separate; GitHub's ordinary Linux runners cannot certify VFX output.

On the default branch, conventional commits since the latest version tag select:

| Commits                                                    | Bump       |
| ---------------------------------------------------------- | ---------- |
| `fix:` / `perf:` (optional scope)                          | Patch      |
| `feat:` (optional scope)                                   | Minor      |
| `type!:` or `BREAKING CHANGE:` / `BREAKING-CHANGE:` footer | Major      |
| No qualifying commits                                      | No release |

`chore: release v...` commits and a head commit containing `[skip release]` do not trigger automatic releases. Versions are plain `MAJOR.MINOR.PATCH`, each component 0–65535, to remain compatible with Chromium manifests. Prerelease version strings are intentionally unsupported.

The planning job computes a candidate without changing the repository. Both build jobs apply that exact version locally and validate/package it. Only after **all required jobs pass** does the release job commit the synchronized versions, create a tag, and publish. It refuses to publish an automatically planned release if the branch advanced during checks. Dependency resolutions remain locked; changing a release version does not regenerate dependency versions. Bot-created commits/tags need not trigger another workflow because the same run already publishes the checked artifacts.

Automatic commits require GitHub Actions `contents: write` and branch rules permitting the bot. Restrictive protected branches may reject the version commit; use the manual tag flow below with your normal reviewed version PR. No bypass token is stored or requested by this project.

## Manual release

In Actions, run **Build and Release**, select a branch, set `release=true`, and choose `bump` or an explicit larger `version`. The same checks and branch-advance guard apply. `release=false` runs validation without creating a release.

For a reviewed tag-based release:

```sh
bun scripts/set-version.ts 0.1.1
# Review, validate, and commit all four versioned files through normal workflow.
git add Cargo.toml Cargo.lock extension/manifest.json package.json
git commit -m 'chore: release v0.1.1'
git tag -a v0.1.1 -m v0.1.1
git push origin HEAD
git push origin v0.1.1
```

A tag must exactly match committed versions. Publication still waits for the full checks. Existing releases can receive replacement checked assets on a rerun; generated notes are retained. `SHA256SUMS` is verified again immediately before upload.

## Artifacts

- `linux-rtx-vsr-vVERSION-x86_64-unknown-linux-gnu.tar.gz`: executable with embedded extension assets, unpacked extension, installer/runtime acquisition script, docs, license and third-party notices. Built on Ubuntu 24.04; require glibc 2.39+ or build from source for an older host.
- `linux-rtx-vsr-extension-vVERSION.zip`: extension files at the ZIP root plus license notices. Extract into a stable directory and use Load unpacked. This is not a signed CRX or a Web Store publication.
- `SHA256SUMS`: SHA-256 for both artifacts.

No NVIDIA driver, CUDA/nvJPEG library, SDK binary, model, browser, downloaded media, or private token is included. Download those separately under their own terms. NixOS uses the source package/runtime wrapper rather than the generic glibc archive.

Local packaging:

```sh
just install
just package
cd dist
sha256sum --check SHA256SUMS
```

Release notes are generated by GitHub from the commit/tag history. Record measured hardware/browser compatibility in the repository before claiming it in release notes. This task prepares automation and local archives; it does not create a remote repository or publish a GitHub release.

Local packages inherit the local toolchain's libc/interpreter. An archive built on NixOS requires its Nix store paths and is a local verification artifact; the GitHub Ubuntu build produces the conventional glibc release binary.
